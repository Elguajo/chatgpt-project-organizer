# Architecture

## Recommended stack

Client/runtime: WXT content script, vanilla TypeScript  
Manifest: MV3 generated by WXT  
UI framework: none  
Application/backend: none  
Database: none  
Auth: none  
Storage: extension local storage (`browser.storage.local` / WXT storage wrapper)  
External services: none in production  
Hosting: Chrome Web Store distribution only  
Testing: Vitest + sanitized DOM fixtures; Playwright/manual browser QA  
Observability: development-only structured console diagnostics, disabled by default in production

## Why this stack

- The product is primarily a content-script DOM augmentation, so React would add unnecessary runtime and integration complexity.
- WXT provides current MV3 packaging/dev ergonomics while keeping the implementation framework-agnostic.
- Local extension storage is sufficient for small project/conversation metadata.
- No backend is required for the MVP and would create privacy, security, cost, and account-system complexity without improving the core job.

## System shape

```text
chatgpt.com
    |
    v
WXT content script
    |
    +--> Route / DOM reconciler
    |       |
    |       +--> ChatGPT DOM Adapter
    |               |- resolve active Project key
    |               |- discover conversation rows
    |               |- derive conversation navigation metadata
    |               |- find safe UI mount points
    |
    +--> Pin Controller
    |       |- pin / unpin
    |       |- order
    |       |- refresh cached visible title
    |
    +--> Storage Repository
    |       `- schema-versioned local ProjectPins state
    |
    +--> UI Renderer
            |- synthetic Pinned section
            |- pin buttons on recognized native rows
            `- accessible events / states
```

## Architectural rule: synthetic pinned section

Pinned chats are rendered as extension-owned navigation rows. Native ChatGPT conversation nodes are **not moved** in MVP.

Benefits:

- avoids fighting React node ownership;
- avoids order resets after ChatGPT re-renders;
- avoids destructive DOM mutation;
- allows pinned entries to remain visible even if the native list is virtualized/lazy;
- makes extension teardown simple.

Native pinned conversations may therefore also remain in their normal location. Duplicate navigation presence is acceptable for MVP.

## Reconciliation lifecycle

1. Content script starts at `document_idle`.
2. Reconciler resolves whether the current page has a recognized active Project.
3. If no Project can be resolved, extension-owned Project UI is removed and no native rows are changed.
4. Adapter discovers visible conversation rows and safe mount point.
5. Storage loads pins for `projectKey`.
6. Renderer mounts/updates one `data-projectpins-root`.
7. Recognized native rows receive idempotent Pin controls.
8. MutationObserver coalesces DOM changes and repeats reconciliation.
9. `popstate`, `hashchange`, visibility return, and relevant DOM mutations trigger a re-check.
10. Unload/disconnect cleans observers/listeners.

Never run an expensive full-document scan for each mutation. Reconciliation must be coalesced with `requestAnimationFrame`, a microtask, or a bounded debounce.

## Storage model

Root key: `projectpins.state.v1`

Conceptual structure:

```ts
type ProjectPinsState = {
  schemaVersion: 1;
  projects: Record<ProjectKey, {
    pins: PinnedConversation[];
    updatedAt: number;
  }>;
};

type PinnedConversation = {
  conversationKey: string;
  href: string;
  title: string;
  order: number;
  pinnedAt: number;
  updatedAt: number;
};
```

`ProjectKey` is adapter-derived. Prefer a stable project token/ID; use a normalized project navigation href only as a fallback.

`ConversationKey` should prefer a stable conversation identifier from its navigation URL; normalized href is fallback.

## Storage migrations

All reads go through one repository.

- Unknown future schema: fail safe and do not overwrite.
- Known old schema: migrate through explicit tested migration.
- Writes are atomic at the state-object level for MVP because data volume is tiny.
- Deduplicate pins by `(projectKey, conversationKey)`.

## DOM adapter boundary

No ChatGPT selector or route pattern outside `src/adapter/`.

Adapter API should expose semantic data, not raw selector logic:

```ts
interface ChatGptDomAdapter {
  resolveContext(): ProjectContext | null;
  findPinnedMountPoint(context: ProjectContext): HTMLElement | null;
  listConversationRows(context: ProjectContext): ConversationRow[];
  decorateTargets(context: ProjectContext): ConversationRow[];
}
```

See `docs/product/DOM_ADAPTER.md`.

## Security boundaries

- Content script is allowed to read only DOM required for navigation metadata.
- Do not read message-body containers.
- Do not inspect cookies/localStorage/auth tokens.
- Do not make network calls.
- Do not use MAIN-world injection unless a future verified blocker proves it necessary.
- No remote scripts/assets.
- No privileged background service worker in MVP unless a concrete need appears.
- Sanitize all strings before injecting: use `textContent`, never untrusted `innerHTML`.

## Permissions

Target production manifest:

```text
permissions:
  storage

content script matches:
  https://chatgpt.com/*
```

No other permission without ADR + change review.

## Styling

- Prefix CSS classes/attributes with `projectpins-`.
- Avoid broad element selectors.
- Prefer inherited typography and CSS variables where safe.
- Keep a small local fallback style so UI stays readable when ChatGPT tokens change.
- Do not ship remote fonts/icons.

## Accessibility

- Pin actions are real `<button>` elements.
- `aria-label` describes Pin/Unpin.
- `aria-pressed` reflects state.
- Pinned links remain regular anchors when possible.
- Keyboard focus indicator must be visible.
- Icon is not the only accessible state signal.
- Localization baseline: English + Russian microcopy; fallback English.

## Performance budgets

Soft targets, verified on normal desktop hardware:

- Mutation callback schedules work, not full synchronous scans.
- Reconcile median under 20 ms for a visible project list of 100 rows.
- One observer for the relevant subtree where possible.
- No per-row intervals.
- Storage writes only on actual state change.
- No memory growth while navigating repeatedly between Projects.

## Scaling assumptions

MVP expected state: tens of Projects, tens of pins per Project. `storage.local` capacity is far above this metadata footprint.

Do not add a database/indexing layer until a real feature requires it.

## Revisit when

- ChatGPT stops exposing stable navigation metadata in the DOM.
- MAIN-world route events become necessary.
- cross-device sync is requested;
- folders/tags require more complex state;
- Firefox/Safari differences become a product requirement;
- OpenAI publishes a supported extension/integration API that can replace DOM dependence.
